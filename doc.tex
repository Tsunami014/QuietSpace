\section{Identifying and Defining}

\subsection{Problem Statement}
% Outline the problem or opportunity that the project addresses. Consider who is affected by this issue.
% Explain why this problem or opportunity is significant.
% Justify the development of a software solution as an appropriate response.
People have increasingly busy lifestyles, and during periods of downtime such as when waiting for public transport, when people are bored, or in many other scenarios - digital platforms have been optimised for user engagement and can increase stress and anxiety. For example, many apps (especially ones paying to show above search results and on the home screen of app stores to be more frequently downloaded) utilise lootboxes, repetitive gameplay loops and constantly make users come back with streaks and limited time events. These features are often created to increase user engagement to provide opportunity for microtransactions and company profit, even though it detriments users. Additionally, the internet is a source for a lot of potentially stressful news and FOMO-inducing social media, among many other things.

This is significant as these increases of stress in an already busy life can lead to negative consequences such as burnout, anxiety and other mental health issues. Developing a space designed to be consistently interesting (through curiosity) yet still relaxing can help solve this problem. Instead of spending free moments playing high-intensity mobile games or scrolling social media, people can instead play this game which decreases stress while remaining rewarding enough to encourage continued engagement. This is practical because it can be used in the same moments of downtime that would be filled with more stressful activities. Ultimately, this may contribute to an increased wellbeing in users by replacing more stressful digital games.

\subsection{Project Purpose and Boundaries}
% Outline what the project is trying to achieve.
The project will provide a relaxing digital space on the internet users can explore and build within. The game will consist of a procedurally generated world that varies in each new world, while utilising relaxing scenery to decrease stress. Exploration and discovery will encourage revisiting without the need for high-pressure limited time or competitive mechanics. Additionally, players will be able to build structures with resources they discover, allowing for freedom of expression. This will be a single-player game focussed on exploration, creativity and relaxation to be played in downtime as opposed to including multiplayer elements requiring having friends available.

\subsection{Stakeholder Requirements}
% Identify stakeholders (client, users, teacher, peers).
% Describe their needs, expectations, and how these influenced the project direction.
The project stakeholders are the users of the game, which in this case is the general public. The game should be easily accessible during short periods of downtime and provide a relaxing experience. It must also remain engaging to encourage revisiting, which influenced the inclusion of the procedural generation, exploration and building mechanics. Additionally, users require a low-stress environment. The need for a low-stress and potentially brief experience influenced the decision to make it single-player, without competitive or limited time elements.

\subsection{Functional Requirements}
% List and describe what the system must do.
The system must do the following:
\begin{itemize}
  \item The game must provide aesthetic visuals intended to create a relaxing atmosphere
  \item Users must be able to make a new world, load an external world or load a world they have played before
  \item Users must be able to export and share their worlds in a secure and private way
  \item Users must be able to walk around in the world
  \item Users must be able to add or remove blocks from the world
  \item Users must be guided on how to interact with the game
  \item The game must be able to save the world the user is in
\end{itemize}

\subsection{Non-Functional Requirements}
% List and describe system qualities such as:
    % Performance, Usability, Security, Reliability
The system must have the following qualities:
\begin{itemize}
  \item The game must be optimised for load times
  \begin{itemize}
    \item Worlds must load within 2 seconds
    \item The game must start up within 2 seconds
    \item Throughout the game chunk loading should not be visible to the user (happening offscreen)
  \end{itemize}
  \item The system must not run into game-breaking bugs or crashes during normal gameplay, ensuring availability
  \item The system must run reliably, handling unexpected errors without interrupting user experience
  \item The UI must be designed to work on various sized screens including both phone and desktop
  \item The website must be playable in any modern browser
  \item The game must store data in a secure location where it is unable to be accessed from outside the website
\end{itemize}

\subsection{Constraints}
% Identify limitations affecting the project, such as:
    % Time, Technical knowledge, Hardware/software access
The limitations on this project are:
\begin{itemize}
    \item I have not created HTML games before and have limited Javascript experience, which may increase development time.
    \item Procedural generation is difficult and time-consuming to feel right, as this is a subjective measure. It may require significant testing and trial-and-error.
    \item I will need to curate a set of assets to ensure the game looks nice, coherent and unique, which will increase development time.
\end{itemize}

\subsection{Requirements Analysis and Prioritisation}
% Analyse the functional and non-functional requirements. In your analysis, consider:
    % - Which requirements were prioritised and why
    % - Trade-offs made due to constraints
    % - How requirements align with the identified problem or opportunity
The functional and non-functional requirements were made to match the criteria outlined in the project purpose section. Requirements such as world generation, exploration and building were prioritised over additional features, visual variety or aesthetic polish as the project is constrained by my limited Javascript experience, complexity of procedural generation and need to make custom assets.

Other features I could have added are for example music and increased variety of tiles and structures. I have not made much art before and even less music, so creating either of these will take a long time and therefore I have prioritised the core functionality instead. While art is required for the game to work, music is not and I have therefore decided not to include it unless I have time.

Overall, prioritising the core functionality allows the app to fit the criteria and still be successful even if not perfect. Although it won't provide as much of a visually distinct experience as I won't be adding many tiles, the world generation and exploration allow for significant replayability while building and world management such as saving and loading allow users to expand creations across multiple sessions. These priorities additionally focus on exploration and creativity rather than competitive or high-pressure mechanics.


\section{Research and Planning}

\subsection{Development Methodology}
% Describe the development approach used (e.g. Agile, Waterfall, WAgile).
% Justify the suitability of this methodology. You could consider...
    % Project size and complexity, Time constraints, Feedback and iteration requirements
The Waterfall approach was chosen for this app due to the complexity in the connection between different systems in the app, including the procedural generation and asset development.

The Waterfall approach is where the development happens step by step, where requirements are established at the start of development and major design changes are avoided throughout development.
This approach ensures the purpose, style and gameplay choices of the app remain consistent and do not overshoot the requirements laid out at the start.
This project fits this approach due to its need for a clearly defined scope and feature set to avoid wasting development time creating assets that don't fit the structure or reworking the generation to fit the assets, which are both extremely time-consuming.
Although the waterfall approach does not allow for much adaptation to incorporate user feedback, this same approach can be utilised for future revisions of the app to improve the design as requested whilst still maintaining quality.

\subsection{Tools and Technologies}
% Justify the selection of software applications, engines, developer tools, programming languages, IDEs, frameworks, libraries and/or hardware components.
% Explain how these tools supported efficient and effective development.
The project will use plain HTML and Javascript without any external libraries, frameworks or game engines.
This was chosen due to its simplicity and compatibility, but additionally because it decreases load time due to reduced dependency loading requirements and reduces vulnerabilities and bugs introduced through external dependencies or upstream changes.
It also allows the app to be statically hosted, creating more hosting options, and makes debugging more straightforward due to the lack of a build process, and easier as browsers include effective built-in debuggers.

This will be developed in neovim due to its efficiency and simplicity for programming and will use Git for effective version control.
I also have extensive experience with these 2 tools, allowing a more efficient and streamlined development experience.

\section{Producing and Implementing}

\subsection{Development Process}
% Describe how the solution was built and implemented.
% Justify the engineering techniques used, such as:
    % Modular design, Object-oriented principles, Reuse of code, Validation and error handling
The solution was built with a modular design in which each feature (e.g. collisions, rendering, and terrain generation) was implemented in a separate file, which reduces interdependencies between modules and overall improves the maintainability of the whole system.
Due to the independent nature of the code, there was minimal code reuse as isolation betwen sections improved debugging by allowing modules to be tested independently.
For example, the collisions module was independent from the other modules and handled only the collision logic, allowing it to be isolated for debugging.
This enabled iterative development and reduced integration complexity during development.

OOP was not utilised as the app did not require complex object hierarchies or abstraction layers.
Each feature operated independently with minimal shared logic or state, and the separation of files using Javascript modules with scoped exports allowed clean interactions between different modules.
This results in a modular architecture that shares some similarities with OOP, particularly encapsulation, without introducing class-based complexity.

Validation and error handling were implemented through built-in Javascript prompts which provide a lightweight, simple and cross-platform solution.
Although these prompts are not visually integrated with the rest of the app, and controlled inputs reduce errors except when loading external world files.
As a result, these prompts are unlikely to impact user experience as they are not seen during normal usage.


\subsection{Key Features Developed}
% Describe the core features of the system.
% Justify their inclusion.
The system contains the following key features:
\begin{itemize}
  \item The core system (in \verb|main.js|) is responsible for loading all modules in their correct order (including drawing the loading screen) and handling the main gameplay loop.
  \item The world display (in \verb|draw.js|) handles rendering the game world each tick. This ensures tiles are drawn in the correct locations, either in front or behind the player as appropriate, and ensures there are no awkward seams between tiles.
  \item The tile loader (in \verb|tiles.js|) is used by the world display to load the tileset and break it into individual tiles for rendering. This also handles tile interaction properties, such as adding borders around some tiles that go into adjacent spaces.
  \item The player (in \verb|player.js|) handles loading the player image, resizing it when needed and drawing it to the screen.
  \item The player physics (in \verb|phys.js|) handles player movement and collision detection. This additionally handles sliding the player along blocks when colliding at an angle.
  \item Mouse interaction (in \verb|mouse.js|) was separated from \verb|main.js| due to its size and complexity. This handles all mouse events, remembering mouse position and drag states, and handles some keypresses to mimic the mouse. It also contains some utility functions for the mouse, for example determining which block the mouse is currently hovering over.
  \item The terrain generation (in \verb|gen.js|) is a core part of the system's design. This includes a custom generation algorithm and handles all the generating and placing of tiles.
  \item The menu/file select overlay (in \verb|filesel.js|) enables changing between different worlds and displaying controls in one place for improved organisation and navigation. This has to auto generate the html for the page contents and transform everything into the correct places.
  \item The loading/saving of worlds (in \verb|worlds.js|) is a key functional requirement of the system. This file handles other world utilities such as renaming, deleting, copying, exporting and importing, handling collisions appropriately.
  \item The backpack (in \verb|bkpk.js|) improves user experience by combining all collected items in one place, simplifying the building process. This was added to resolve earlier confusion around requiring multiple clicks to select a decoration, which was unintuitive to all testers and difficult to succinctly explain. This file handles discovery of blocks and backpack with block selection, including the discovery popup.
\end{itemize}

\subsection{Back-End Engineering Contribution}
% Explain how back-end engineering contributed to the success and ease of use of the software, including:
    % Data processing, Validation and logic, Storage and retrieval, Authentication (if applicable)
The back-end engineering in the storage and retrieval of worlds allows users to access multiple saved worlds, each containing different gameplay content.
This improves the diversity of gameplay experiences since a single world may not cover the full range of available content.
It additionally enables the separation of creations into multiple worlds, increasing the available building space for users.
This allows users to make backups of worlds to revert to a previous state and reduces the impact of user errors, making the game more forgiving.
Sharing worlds with others also promotes the game and contributes to its success.

\subsection{Version Control Summary}
% Summarise commits, iterations, or sprints if version control was used.
Initially, the tile rendering, movement, and a loading screen were implemented.
Afterwards, terrain generation was implemented and the renderer was further optimised.
The player was implemented, and an issue was identified where tile rendering was off-centred, which was subsequently fixed.
Player collision was added alongside multilayer rendering for tall objects (initially using a tree) to allow the player to move in front of or behind objects.
Later stages involved various improvements, including block selection and placement with a highlighted cursor, improved player controls and a hotbar.
Afterwards, a journal was added as an intro to the game, including bookmarks and world saving and loading functionality.
Minor improvements were then implemented, including world renaming, deletion and improved back-end functionality for journal pages.
Then a rule-based tile generation system was implemented to significantly reduce generation and placement complexity.
Exporting and importing worlds were implemented, alongside general bugfixes and minor improvements.
A backpack was then added with a block discovery system, improving aspects of the previous design that testers found inconvenient or confusing.
Lastly, more back-end improvements were made to the journal and compilation was introduced to speed up loading.


\section{Testing and Evaluation}

\subsection{Testing Methods Used}
% Describe testing approaches, such as:
    % Unit testing, Integration testing, User testing
% Explain how testing results were used to improve performance, efficiency, or reliability.
Testing was conducted through unit, integration, system, and user testing.
To ensure individual modules worked, the codebase was stripped of features that interfered with testing.
For example, the generation algorithm was occasionally stripped down to alternating tiles for clearer visibility of tile boundaries which helped while testing tile interaction components.
Unit testing was conducted by repeatedly performing actions and verifying that outputs matched expected results.

\subsection{Evaluation of Social, Ethical and Communication Issues}
% Evaluate your project in terms of
This game effectively addresses social, ethical and communication issues present in both game design and also in other mobile apps, resulting in a positive impact on individuals' wellbeing, autonomy and accessibility.

The game addresses many of the social and ethical issues found in mobile apps by providing a relaxing environment that encourages exploration and curiosity.
This game does not utilise repetitive and mindless gameplay or manipulative, FOMO-inducing mechanics such as streaks, limited time events, and pay-to-win systems.
Such mechanics are designed to encourage compulsive engagement and are commonly found in social media and many mobile games.
Instead, this game utilises intrinsic motivation through discovery and creativity to encourage voluntary revisiting, reducing negative impacts on mental health and promoting relaxation and wellbeing.
It can help further improve mental health by replacing time spent on other addictive or stress-inducing apps during the same period of downtime.
Because the game does not include leaderboards or social elements, users are encouraged to share their progress only when and how they choose, helping minimise social comparison.
Worlds are also completely private and exports are password-protected, giving users control over who they share their worlds with and how, which supports user autonomy.
Overall, these features demonstrate the game's positive social and ethical impact by addressing these problems commonly found in mobile apps and games.

The game does not use a traditional onboarding process; instead, controls are progressively shown to the user throughout the journal, even on subsequent launches.
This allows users to easily refresh their memory of the controls, but means the instructions take up more space than if they were in a separate section after the first load.
This impact is reduced by the short length (being only two pages) and as users can utilise keybinds to avoid this issue entirely.
Additionally, the controls are intuitive because the game uses common and adjacent keys, further reducing the likelihood of user confusion.
This mitigates communication issues because controls are consistently available and easy to remember, reducing frustration while improving accessibility.

\subsection{Secure Software Design and Data Handling}
% Evaluate the approach undertaken to safely and securely collect, use, and store data.

        % Secure coding practices applied during development
        % Input validation and error handling
        % Data storage and protection methods
        % The impact of secure software design on user trust, data integrity, and system reliability
The codebase was developed utilising secure coding practices to minimise data breaches.
All inputs and the URL itself do not get executed, reducing the risk of XSS attacks.
All external inputs such as world loading are also validated, ensuring errors are caught before they can cause damage to the system.
Additionally, save data is stored in the page's local storage, meaning no other websites can access the data due to same-origin protections.
Encryption was also applied to exported worlds, allowing users an extra layer of security when sharing their creations online.

All these security aspects reduce the likelihood of unauthorised data access, increasing system reliability and integrity as security incidents are reduced, which in turn improves user trust.
